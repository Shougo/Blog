## はじめに

私は今回 Linux 向けの Neovim GUIとして「ng」を作りました。Go で書いた、最小限の GUI クライアントです。

https://github.com/Shougo/ng

ng は Neovim の上に新しいエディタを作るものではありません。Neovim のための、ただの UI です。GVim が Vim にとってそうであるように、ng は Neovim に GUI の窓を与えるだけです。

- リポジトリ: [Shougo/ng](https://github.com/Shougo/ng)
- ライセンス: MIT
- 対応: Linux（X11 と Wayland）、Neovim の最新安定版と nightly

この記事では使い方よりも、ng が「何を作らないと決めたか」と、それによって何が得られたかを中心に書きます。

## なぜ Neovim GUI を作ったか

私が以前から欲しかったのは、端末で使う Neovim と同じ画面が、端末より速く表示でき、日本語を正しく扱える Neovim GUI でした。
しかし、Neovim 登場から 10 年以上の時が経ったにも拘わらず、自分が満足のいくものは全く登場していません。

私はこれまでに既存の Neovim GUI をいくつも試しましたが、多くは Neovim を土台にした「新しいエディタ」を目指しています。スムーズスクロール、アニメーションするカーソル、独自のタブやポップアップといった機能は一見魅力的です。一方で、画面の更新が端末より遅くなったり、変換中の日本語が崩れたりと、基本的なところで困ることがありました。

理想に近かったのは Windows の Nvy です。画面をそのまま出し、余計なことをしません。Linux にもそういう GUI が欲しかったので、生成 AI を使って自分で作ることにしました。

https://github.com/RMichelsen/Nvy

Neovim GUI を作り始めた人の多くが、エディタ一式を作ろうとして途中で止まっています。ng はその逆を行き、最初から「作らないもの」を決めました。

## 作らない機能

名前の ng にはいくつか意味を込めています。"New GUI"、"Neovim GUI"、"Neovim in Go"。そして日本語の「NG」です。ほとんどの機能は、あえて実装していません。
「実装しない」ことこそ ng の新規性だと思っており、そのおかげで幾つかの利点を得ました。

| 実装しない機能 | 代わりに得た利点 |
| --- | --- |
| ext_multigrid などの ext_* 拡張 | 端末と同じ画面。正しさをテストにより機械的に確認できる |
| アニメーション、スムーズスクロール | キー入力がすぐ画面に反映される |
| 専用の設定ファイル | 設定は Neovim のオプション（guifont など）、`g:ng_*` 変数、コマンドライン引数だけ |
| 独自のタブ、ポップアップ、ウィジェット | GUI ツールキットに依存せず、小さく保守できる |
| Windows と macOS 対応 | Linux の X11 と Wayland をきちんと動かすことに集中できる |

専用の設定ファイルを持たないのは、GVim と同じ考え方です。フォントは `guifont` と `guifontwide` オプションで指定し、GVim の書式もそのまま通ります。ウインドウの大きさも `:set columns` と `:set lines` に従います。設定はすべて Neovim の設定ファイルに集約されるので、端末と ng で設定を分ける必要がありません。

ng にはどうしても必要な機能だけを実装しました。具体的にはフォントと CJK の表示、IME、Neovim 最新版への追従(`:restart` 機能への対応など)、クリップボードからの貼り付け、タイル型ウィンドウマネージャへの対応、それに ng が落ちても Neovim が生き残り、`ng --server` でつなぎ直せることです。
これらは一見地味ですが、日常の使い勝手を左右するので重要です。

## 端末と同じ画面

ng は Neovim の UI プロトコルのうち ext_linegrid だけを使い、端末の Neovim（TUI）と同じ画面を表示します。フローティングウインドウもコマンドラインも、Neovim が描いた 1 枚のグリッドとして届きます。

この制約には、TUI のように描画された画面が正しいかをテストで機械的に確かめられるという利点があります。Neovim 自身に `screenstring()` で画面の文字を尋ね、ng が保持している画面と比べればよいからです。ng の統合テストはこの方法で、日本語や全角記号を含む画面、スクロール、サイズ変更などを検証しています。CI では Neovim の安定版と nightly の両方に対して、毎日このテストを回しています。

ext_* 拡張を使って GUI 側で画面を組み立てると、「正しい画面」の定義が GUI ごとに変わります。そうなるとこのような検証はできません。「端末と同じ」という制約が、そのまま仕様書となりテストの答えになっています。

プラグイン作者にとっても、端末で動くものが ng でもそのまま動きます。ng 専用の対応は必要ありません。

## 速さ

ng では応答速度も重要視しました。キーを押してから画面に出るまでは、ng の内側で中央値 7.95ms、10 回中 9 回は 8.5ms 以内です。60Hz の画面の 1 フレーム（16.7ms）の半分ほどです。

自分の設定とプラグインで普段どおり編集した 176 回のキー入力を、`ng --trace` で測った結果です（Manjaro Linux、Neovim 0.13 nightly）。

| 区間 | 中央値 (ms) | p90 (ms) | 最大 (ms) |
| --- | --- | --- | --- |
| 全体（キーイベントから表示まで） | 7.95 | 8.46 | 121.90 |
| SDL のキューでの待ち | 0.14 | 0.20 | 0.82 |
| Neovim の応答 | 0.72 | 1.00 | 106.18 |
| 描画と表示 | 6.99 | 7.40 | 15.47 |

20ms を超えた 3 件は、すべて Neovim 自身の処理でした。コマンドラインに入る `:`、コマンドを実行する Enter、それにマッピングです。これは端末でも同じだけかかります。

「描画と表示」のうち 4ms は、わざと待っている時間です。Neovim は 1 回の変更を複数回の flush に分けて送ることがあり、そのたびに表示すると、補完中にコマンドラインが一瞬消えるようなちらつきが出ます。端末はリフレッシュレート単位で書き換えるので、途中の画面を見せません。ng も「Neovim が 4ms 静かになるまで、ただし最大 16ms」待ってから表示します。この値は、実際のトレースで計測した flush の間隔から決めました。

ng 自体の起動も高速化しました。最初は起動が遅かったのですが、Neovim の起動と接続、フォント情報の読み込み、ウインドウの作成を並行して行うようにしました。設定の読み込みが終わった最初の画面からウインドウを見せます。ウインドウが出た瞬間に色やフォントが切り替わることはありません。

## 日本語対応について

日本語への対応は、ng が数少ない「こだわって作る」と決めた部分です。

**表示**。全角文字は 2 セルに、幅の曖昧な文字は `ambiwidth` に従って描きます。どの文字もセルに収まるように拡大縮小して中央に置くので、欧文フォントと和文フォントの大きさが違っても行がずれません。`guifontwide` には別のフォントと大きさを指定できます。フォントは FreeType で直接読むので、"Courier 10 Pitch" のような TrueType や OpenType ではない古い Type 1 形式のフォントもそのまま使えます。これは Skia を土台にした GUI では読めないことがある形式ですが、ng なら GVim で使っていたフォントがそのまま使えます。

**IME**。fcitx5 や IBus など、システムの IME を SDL 経由で使います。

- 変換中の文字は ng がカーソル位置に、本文と同じフォントで描きます。候補ウインドウもカーソルの位置に出ます。
- 変換中の Enter や Esc は IME に渡り、確定した文字だけが Neovim に届きます。
- IME を効かせるのは、挿入モードやコマンドラインなど文字を打つモードだけです。IME をオンにしたまま Esc でノーマルモードに戻っても、そのまま `dd` や `:w` が効きます。Neovim のモードを知らない端末にはできないことです。

ただし X11 での挙動には制限があります。SDL は X11 では XIM だけを使うので、日本語の変換はできますが、変換中の文字は IME のウインドウに出ます。カーソル位置に直接変換中の文字を描けるのは Wayland です。この制限は dbus-monitor で確認し、README に記述しています。

## 技術選択: Go と SDL3 と cgo の採用

ng は Go で実装し、ウインドウ生成とキー入力には SDL3、文字の描画には FreeType と fontconfig を使っています。いずれも Go のバインディングは使わず、C の API を cgo で直接呼ぶことにしました。

Neovim GUI にウィジェットは本来要りません。GUI が描くのはテキストを表現する文字のグリッド 1 枚だけです。だから GTK や Qt のような大きなツールキットではなく、ウインドウとキー入力だけを扱う SDL3 を選びました。文字はグリフをテクスチャにまとめ、変わった行だけを描き直しています。

Go のバインディングを使わないのには理由があります。

- **ライブラリの寿命**。大きなツールキットにはサポートの終わりがあります。Qt 5.15 は 2025 年 5 月に標準サポートを終えました。更に Go のバインディングはそれより前に開発が止まりがちで、開発が停止するとライブラリ利用側が抜け出せなくなります。
- **実装の小ささ**。使う関数だけを小さな C のヘルパーにまとめているので、SDL の更新に追従する手間が小さく済みます。
- **安定性**。SDL3、FreeType、fontconfig は、ディストリビューションが保守する枯れた C のライブラリです。Neovim との通信（msgpack-rpc）は標準ライブラリだけで記述し、外部の Go パッケージには依存していません。

Go で GUI を書くときの厄介な問題に、スレッドがあります。多くの GUI ライブラリはメインスレッドからしか触れませんが、goroutine はどのスレッドで動くか分かりません。ここを誤ると、時々しか再現しないクラッシュやデッドロックになります。これを防ぐため、ng はルールを 1 つに絞りました。

- SDL に触るのはメインスレッドだけ。
- Neovim との通信など他の goroutine は、仕事をキューに積んで SDL のイベントでメインスレッドを起こすだけ。
- コールバックは使わず、メインスレッドが自分でイベントを取りに行く。

C から Go が呼ばれることがないので、この種のバグは設計の時点で起きません。これができるのも、描くものがグリッド 1 枚だけだからです。複雑な UI を作らないという最初の意思決定が、Neovim GUI の実装として Go を選べる理由にもなっています。

## ng を使ってみる

ng は SDL3、FreeType、fontconfig を入れて、`go install` でインストールできます。標準的な環境として Arch Linux、Fedora、Debian でのビルドは CI で毎日確かめています。

```sh
# Arch Linux / Manjaro
sudo pacman -S sdl3 freetype2 fontconfig go
# Fedora 42 以降
sudo dnf install SDL3-devel freetype-devel fontconfig-devel golang gcc
# Debian 13 以降、Ubuntu 25.04 以降
sudo apt install libsdl3-dev libfreetype-dev libfontconfig-dev golang-go gcc pkg-config

go install github.com/Shougo/ng/cmd/ng@latest
```

ng の使い方は Neovim と同じです。

```sh
ng file.txt                 # Neovim を起動して開く
ng --server                 # ウインドウが落ちた Neovim につなぎ直す
ng --trace /tmp/ng.log      # 不具合の報告や遅延の計測用
```

ng のフォントは、いつもの Neovim の設定に記述します。

```vim
set guifont=Courier\ 10\ Pitch:h12
set guifontwide=Noto\ Sans\ Mono\ CJK\ JP:h12
```

アプリケーションランチャー用の `.desktop` ファイルとアイコンは、リポジトリの `assets` にあります。

## おわりに

今回、ng の実装には AI (Claude Code)を使いました。私は「AI に実装を任せるとイノベーションが生まれないのではないか」、と言われたことがあります。確かに ng は画期的なソフトウェアではありません。やっていることは地味です。
でも、それでよいのです。こういう Neovim GUI が今までなかったのは、新しさがなく地味だからだと思います。GUI は GUI の役割を果たしてくれればそれで十分です。

私が常々思っていることがあります。ソフトウェアを AI で作ったから品質が低いのではありません。AI を使って品質を下げたものの品質が低いのです。例えば同じ中国で作られた商品であっても、検品していないような最初から壊れた商品も、iPhone のような高級品も両方が存在します。
これらの違いは、検証にどれだけ時間とお金をかけたかです。ソフトウェアも同じで、AI もちゃんと使えば時間もお金もかかります。皆が AI を使って手を抜こうとばかり思っているから「AI slop」という悪口が生まれるのだと思います。
ng は実機で日本語を打って試し、トレースで計測し、統合テストを毎日回しています。開発にはかなりの労力がかかっています。AI が実装を間違えたところもありましたが、そういう地道な検証で見つけて直してきました。

この地味さは、ソフトウェアの保守とよく似ています。保守が嫌われるのは、仕事に新鮮さがなくて飽きてしまうからでしょう。でも私は保守作業も楽しいと思っていますし、ソフトウェアが少しずつ良くなっていく様子を見るのが好きです。ソフトウェアが使われる期間のほとんどは、作った後の保守の期間です。

ng が余計な機能を足さないのは、そのためでもあります。機能を足して目新しさを追うのではなく、同じものをひたすら磨き続けます。「端末と同じ画面」という制約が、テストの答えになり、Go で GUI を書ける理由になり、速さの理由にもなりました。そして何より、長く保守できる理由になっています。NG な機能がたくさんあるのは、意図したものです。

今後足す予定の機能は、Neovim 0.13 の `vim.ui.img` を使った画像表示だけです。もしなにか不具合があれば GitHub の Issue で教えてください。そのときは `ng --trace` のログを添えてもらえると助かります。
